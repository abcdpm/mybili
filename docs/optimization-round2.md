# 第二次大优化 · 专题方案（第 12、23 项）

## 一、评论下载调度优化方案（第 12 项）

### 病根分析（已实测确认）
| 环节 | 旧版行为 | 后果 |
|---|---|---|
| 投递 | 每天 3:00 **一次性**投递当日全部任务（约 730 个） | 瞬时堆积 |
| 执行 | 每任务 `sleep(3-5)` + 分页抓取 `usleep`，单任务 1-5 分钟 | worker 被 sleep 空占 |
| 并发 | comments 队列仅 **2 个 worker**，日吞吐约 500-900 个 | **入 > 出，逐日累积** |
| 选取 | `--percent=3` 按总数百分比取最久未更新的 | 数据增长后配额不自适应 |

### 已实施（本次提交）
1. **错峰投递**：`--interval` 控制相邻任务投递间隔（默认当日任务均匀摊到约 20 小时），
   等待成本从 worker 转移到延迟队列；
2. **任务内 sleep 归零**：不再阻塞 worker；
3. **评论数聚合预取**：N 次 count → 1 次；
4. 定时参数 `--sleep=0`，附中文调度说明。

### 容量模型（配置建议）
```
日吞吐 ≈ worker数(2) × 86400 / 单任务均时(180s) ≈ 960 个/天
日配额 = 有效视频总数 ÷ 轮换周期天数   （如 24000 ÷ 30 = 800/天 ✔️ 在吞吐内）
```
**配额永远不要超过日吞吐**，否则换任何调度都会堆积。

### 后续配套（并入第 15 项「评论下载设置页」实施）
| 配置项 | 建议默认 | 说明 |
|---|---|---|
| 轮换周期（天） | 30 | 每 30 天全量刷新一遍评论（满足"不同时期评论不同"诉求） |
| 每日上限 | 自动 = 总数/周期 | 可手动压低；上限保护 |
| 投递间隔 | 自动摊 20h | `--interval` 显式覆盖 |
| 条数策略 | 自适应 | 固定条数 / 自适应（现有 log 模型）/ 增量追加 |
| 增量更新条数 | 20 | 在现有基础上追加 N 条（衰减模型） |
- 观测：`app:download-all-comments --status` 增加"轮换周期实际天数/积压量/最近完成时间"；
- 断点续跑：`comments_updated_at` 已是游标，天然支持中断后继续（选最久未更新优先）。

# 第三批设计注意事项（2026-10-23，评审确认）

## 1. 视频连播与分P的 UI 冲突约束（P0 设计红线）

**优先级：分P连播 > 同收藏夹连播。** 设计规则：

1. **分P优先**：当前视频存在多分P时，连播按钮/逻辑默认作用于"当前视频的下一个分P"，播完全部分P后才进入收藏夹连播；
2. **UI 不冲突**：连播开关是单一状态（不出现两个开关），旁边以胶囊标签显示当前连播范围（"分P连播中 P2/4" 或 "收藏夹连播中"）；
3. **播放清单侧栏**：分P列表置顶区域固定，收藏夹连播清单在其下方分组展示，当前播放项高亮并自动滚动到可视区；
4. **播放器状态机**：`ended` 事件处理顺序 = ① 下一分P → ② 播放清单下一项（若开启连播） → ③ 停止并显示重播按钮；用户手动暂停/停止后不自动续播。

## 2. 缓存数据保护红线（评论/弹幕）

所有优化设计**不得删除**用户已缓存的弹幕与评论数据：

- 弹幕文件（`danmaku_files` + `storage/danmaku`）、评论库（`comments`/`comment_users`/`emotes`）只增不删；
- gif 表情修复采用"读取期派生修正"（EmoteResolver 按扩展名派生路径），无需迁移或重写历史数据；
- 任何 schema 变更必须走 migration 向后兼容（只加列/加索引/新表），禁止 DROP/RENAME；
- 迁移类命令（如评论库拆分）必须 opt-in 且可回滚，旧库保持只读兼容。

## 3. 代码注释规范（项目统一）

1. **类级 docblock**：说明职责、设计要点与关键权衡（如批量 upsert 的 OR 冲突语义、指纹缓存免失效原理）；
2. **方法级 docblock**：public/protected 方法必须注明参数、返回结构、异常行为；private 方法在逻辑非显然时补注；
3. **行内注释**：解释"为什么"而非"做什么"；关键修复以【核心修复】【性能】【兼容性】标记，便于回溯；
4. **格式统一**：中文注释、PHPDoc 标准标签（@param/@return/@var）、对齐风格与所在文件保持一致。

## 4. 已实施的全局任务优化（本批）

| 优化点 | 实施 |
|---|---|
| 全局任务自动跳过已失效视频 | `DanmakuDownload` 批量查询加 `invalid=0` 过滤（显式指定 video_id 不过滤）；`CheckVideoPartFileToDownloadAction` 入队闸门跳过失效视频，终结"反复入队→失败"空转 |
| 历史遗留无法下载完成的视频 | 根因=失效视频无限重新入队；新增 `app:download-diagnose` 命令：分类报告 + `--prune-invalid`（队列行标记 cancelled）/`--reset-stale`（滞留 running 重置 pending），**不删除任何媒体与业务数据**，默认只读 |
| gif 动图表情包 | 修复 resolver 对动图派生不存在 .webp 的裂图问题（读取期修正，历史数据自动受益）；优化器本身正确跳过 gif/webp/APNG 动图转换 |
| 系统信息准确性 | 数据库大小改 PRAGMA page_count×page_size（旧估算低估约 76 倍）；PHP 版本如实上报 Web 运行时（FrankenPHP 内嵌）与 CLI 双版本 |
| Telegram 配置 | 补齐默认值预设、前端启用前置校验、422 错误友好化；移除泄漏 token 的调试日志 |

# 批F·架构收官（2026-10-23）运维与回滚预案

## 1. 评论库拆分独立 SQLite（`app:split-comments-db`）

**上线步骤（生产，零删除、可回滚）**：
1. 低峰期执行 `php artisan app:split-comments-db`（只读报告）确认两库统计；
2. `php artisan app:split-comments-db --execute`：复制（源库真实文件时走 ATTACH SQL 级批量复制，
   零 PHP 物化、恒定内存）→ 增量补偿 → 双重校验（行数+内容聚合+20 行抽样）→ 校验通过才写标记切换；
3. 校验不通过自动中止（主库保持权威），修复后低峰重跑即可；
4. 建议同时暂停评论下载任务（定时任务配置页可临时停用 `comments_download`），
   避免迁移窗口写入竞态；即使有竞态，增量补偿 + 二轮复核也会兜底。

**回滚预案**：`php artisan app:split-comments-db --rollback`
- 仅删除标记文件（`storage/app/comments-db-split.json`），读写立即切回主库旧表；
- `comments.sqlite` 文件保留（不删除），可作对照或下次迁移起点；
- 注意：拆分后新写入独立库的增量不自动回流主库（回滚前如有新数据请评估比对）。

**兼容性**：未执行拆分的环境一切行为与旧版一致（连接路由按标记自动选择）；
主库三表永远保留（只读遗留），满足"旧版本向上自动升级 + 不删数据"红线。

## 2. getVideosCache Redis List 分块（P0 内存）

- 新键 `video_list:v2`（List，500 条/块）+ `video_list:v2:total`；旧键 `video_list` 不再写入、
  按原 TTL（1 天）自然过期，期间双读兼容（v2 优先）；
- 读取端 `/api/progress?limit=` 只解码命中的 2-3 个分块，内存 ~1MB（旧版全量解码 50-100MB）；
- 无需运维动作：下次缓存重建（视频数据变更触发）自动写入 v2；
- 回滚：删除 v2 两键即回旧版读取路径（旧键届时如已过期则触发重建），同样零删除业务数据。
